Testing

Test Scope

This project tests the QLIB ↔ OP-TEE integration and the secure storage data path. The boundary is clearly defined:

In Scope (Winbond tests)Out of Scope (upstream / customer)
QLIB authenticated session (connect, load key, open session)PKCS#11 TA crypto correctness (RSA/EC math)
LittleFS backend (mount, write, read, delete, reboot recovery, format-on-first-boot)OP-TEE kernel integrity & isolation
PKCS#11 token init → keygen → sign → verify via W77Q/T backendTF-A (BL2/BL31) secure boot validation
Data persistence across reboot and tee-supplicant restartLinux kernel / driver security
Flash wear & sector-level data correctnessU-Boot chain of trust
SPI bus correctness (RPC-IF register access)Network/application-layer security

Installation Verification

After flashing a board for the first time (or after a major update), run the stage-by-stage installation check to confirm every layer of the stack is operational:

# On the target board:
verify-install.sh
# or with detailed output:
verify-install.sh --verbose

The script checks 7 stages in order and stops reporting useful diagnostics at the first failure:

StageCheckWhat a Failure Means
1OP-TEE device (/dev/tee0)BL32 did not load — check BL31→BL32 handoff, DTB
2tee-supplicant runningDaemon not started — check systemd service
3libckteec.so presentoptee-client not installed — rebuild rootfs
4PKCS#11 TA deployedTA binary missing — check optee-os build
5Slot enumerationTA won't load — check tee-supplicant logs
6W77Q/T flash reachable (QLIB connect)SPI/LIFEC issue or keys not provisioned
7Key generation (full path)Storage path broken — check dmesg for OP-TEE panics
Rule of thumb: Fix the first failing stage before investigating later ones. Each stage depends on the previous stages being functional.

2. On-Board Target Scripts (tests/target/)

Shell scripts executed directly on the Sparrow Hawk board. Each ftNN-target.sh is the on-board counterpart invoked by the host-side test. Common helpers are in common.sh.

# Run all target tests on-board:
/usr/bin/run-all-tests.sh

Running the Full Suite

From a host PC (recommended)

# Connect to board via serial, run all tests, produce JUnit XML:
python3 tests/host/run_integration_suite.py \
    --port /dev/ttyUSB0 \
    --deploy \
    --output test-results.xml

Subset / skip specific tests

# Run only PKCS#11-specific tests:
python3 tests/host/run_integration_suite.py --tests FT22,FT25,FT26

# Skip the slow RSA-4096 test:
python3 tests/host/run_integration_suite.py --no-rsa4096

On-board quick check

# SSH to the board and run the smoke test:
check-pkcs11.sh

Test Output

The integration suite produces a JUnit XML report (test-results.xml) compatible with CI systems (GitLab, Jenkins). Each test case has PASS/FAIL status, duration, and stdout/stderr capture for diagnosis.

What a PASS Means

A passing test suite confirms:
  • QLIB can establish an authenticated session with the W77Q/T chip
  • The LittleFS backend correctly mounts and preserves read/write/delete behavior across reboot scenarios
  • PKCS#11 objects (keys, certificates) survive reboots
  • Flash block allocation and wear-leveling behavior remain consistent with configured LittleFS geometry
  • The SPI bus operates correctly at the register level
It does not certify the cryptographic correctness of upstream OP-TEE algorithms, nor does it validate secure boot or Linux kernel integrity.
